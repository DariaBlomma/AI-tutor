# Правила стиля кода (TutorAI)

Файл пополняется по мере развития проекта. Разделы: общие правила, фронтенд, бэкенд.

---

## Общие правила (проект)

1. **Процесс работы**
   - План составляется только по запросу; код меняется только по явной команде.
   - Коммиты — только по явной просьбе.
   - После правок обязательная проверка: `npx tsc -b && npm run build` (фронт).
2. **Название коммита**
   - Формат: `front: <описание>` либо `back: <описание>` — префикс зависит от того, где делались доработки; после двоеточия — описание на английском.
   - Пример: `front: profile page for teacher and student`.
3. **Контракт API**
   - Типы DTO на фронте зеркалят Java-DTO бэка; не создавать самодельные обёртки ответов (например, `{ success, data }`).
   - Пути фронта зеркаляют зоны API и права доступа бэка (`/teacher/**` защищён ролью TEACHER → фронтовый путь `/teacher/reports`).
4. **Данные и состояния**
   - Моки запрещены на «готовых» страницах; временная вёрстка с моками допускается только под флагом `SHOW_TMP_DATA` (true — показывать мок, false — скрывать до реализации).
   - Роли и ID брать из токена/сервиса, не городить отдельные эндпоинты «узнать свою роль».

## Фронтенд (React + TypeScript + Vite + TanStack Router)

### 1. Структура модулей
- Каждый доменный модуль (`auth`, `teacher`, `student`, `user`…) — отдельная папка в `src/`.
- Внутренняя структура модуля:
  - `ui/views/<ViewName>/` — папка с именем компонента, внутри `<ViewName>.tsx` + `<ViewName>.module.scss`.
  - `hooks/` — логика загрузки/состояний (выносим из компонентов!).
  - `services/` — работа с API.
  - `types/` — модели данных модуля (`models/`, реэкспорт через `index.ts`).
  - `data/` — статичные данные/моки (только под `SHOW_TMP_DATA`).
  - `layouts/` — переиспользуемая вёрстка **без логики**.
  - `widgets/` — смысловые части **с логикой**.
- Общее между модулями → в `shared/` (`widgets`, `icons`, `ui-kit`, `layouts`, `services`).
- Не путать: если переиспользуется только вёрстка — это layout, а не widget. Название файлов/классов должно отражать роль (`AuthTriangleFormLayout`, а не `...Frame`).

### 2. Именование
- Компоненты-страницы: суффикс `View` (`TeacherHomeView`, `AuthLoginView`).
- Хуки: префикс `use` + глагол (`useTeacherReports`, `useTeacherName`).
- Сервисы: `<Домен>Service.ts`, методы — глаголы (`getProfile`, `getReportsOverview`).
- Иконки: префикс `Icon` (`IconHome`, `IconReports`).
- Типы пропсов: `<ComponentName>Props`.
- Константы: UPPER_SNAKE (`USER_PATH`, `SHOW_TMP_DATA`).

### 3. Пути и импорты
- Алиас `@/` для всех импортов вне текущей папки; относительные — только внутри одной папки.
- Избегать циклических импортов типов; тип живёт у владельца домена (`UserRole` → `@/user/types`, а не `@/auth/types`).
- Префиксы путей контроллеров выносить в константу сервиса: `const USER_PATH = '/user'` — дальше не дублировать строку.

### 4. UI-kit, формы, стили
- Все инпуты — только базовые компоненты из `shared/ui-kit` (`BaseInputText`, `BaseInputPassword`). Ошибки поля рендерит сам инпут; серверные ошибки — в слот notice лэйаута.
- Плейсхолдеры в инпутах — на русском языке.
- Единый стиль auth-страниц: белый заголовок сверху, SVG-каркас (треугольники), футер со ссылками внизу — всё через общие layouts.
- Стили — CSS-модули (`*.module.scss`); использовать общие CSS-переменные темы (`--p`, `--pd`, `--bg`, `--c1`, `--c3`, `--r`), палитры страниц и макетов унифицированы.
- Размеры иконок задавать пропсами `width`/`height` (со значениями по умолчанию), чтобы легко менять централизованно.
- После рефакторинга удалять из `.module.scss` все неиспользуемые правила.
- Файл компонента — не место для типов и статичных данных: выносить в `types/` и `data/` внутри папки виджета/компонента (пример: `shared/widgets/AppBottomNav/{AppBottomNav.tsx, types/, data/}`).

### 5. Данные и состояние (компоненты)
- Запрещена «облепиха» логики внутри компонента (fetch + подписки прямо в теле) — выносить в хуки модуля: они тестируются, fetcher можно внедрять параметром.
- Глобальные элементы интерфейса (нижняя навигация `AppBottomNav`) размещаются в `LayoutRoot`, а не внутри отдельных страниц; активный пункт определяется через `useLocation`.

### 6. Роутинг и guard
- Централизованный guard в loader'е `__root.tsx`:
  - нет сессии → редирект на `/auth/login` (не на sign-up);
  - есть сессия + любая `/auth`-страница (включая forgot/reset) → редирект на `/`;
  - на `/` рендер по роли: учитель → `TeacherHomeView`, остальные → `StudentHomeView`.
- Локальные дублирующие редиректы в страницах запрещены.
- Проверка сессии при входе — `AuthService.checkSession()` (валидация токена + попытка refresh).

## Бэкенд (Spring Boot, Java)

> Правила формируются по мере развития; текущие наблюдения:

### 1. Структура (`com.aitutor.backend`)
- Слои: `controllers` → `services/<домен>` → `repositories/<домен>` → `entities`.
- `dto/<домен>` — контракты ответов/запросов; `mappers/<домен>` — конвертация entity ↔ dto; `enums` — словари; `security` — JWT/роли; `configs`, `helpers`, `exceptions`.
- Схема БД — Liquibase changelogs в `resources/db/changelog`.

### 2. Контракты и роли
- Авторизация: access/refresh токены; logout — `POST /auth/logout { refreshToken }`, refresh — `POST /auth/refresh { refreshToken }`.
- id учителя/ученика брать из токена, не из query-параметров.
- Ответы контроллеров — «чистые» DTO без обёрток (фронт не должен изобретать `{ success, data }`).
- Расширение DTO согласуется с фронтом (пример: уровни отчётов — `assignedCount`, `inProgressCount`).
